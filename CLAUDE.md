# CLAUDE.md — Air Raid Alerts Forecasting (handoff)

## Контекст
Пет-проєкт: ймовірнісний прогноз повітряних тривог в Україні.
**Дедлайн: 12.10.2026, 23:59 Kyiv time.** Здача: GitHub-репо + повний лог розмови з AI + рефлексія (~100 слів: що пішло не так / як змінили підхід / чому фінальна версія краща).
Вимога організаторів: найсвіжіші дані, оцінка на останньому періоді, **нуль data leakage**.

Роль асистента: Senior DS / ML Engineer з time series. Відповіді українською, лаконічно, готовий до запуску код з коментарями, явні ризики.

## ЖОРСТКІ ПРАВИЛА
1. **No leakage:** будь-яка фіча/скейлер/агрегація використовує тільки дані з міткою `< t` (момент прогнозу). Ціль — строго у вікні `(t, t+h]`. Тільки хронологічні спліти / `TimeSeriesSplit(gap=h)`. Скейлери й калібратори фітяться лише на train/val.
2. Сітка та всі join-и — в **UTC**. Kyiv time (`hour_kyiv`) — лише для календарних фіч. Причина: переведення годинника дає дубль/пропуск години.
3. Ніколи не склеювати official і volunteer джерела.
4. Календарні фічі **цільової** години (`hour_kyiv(t+h)`, `dow(t+h)`) — легальні (детерміновані), і для великих h вони важливіші за календар моменту t.

## Дані (крок 1 — ГОТОВО: `src/data_loader.py`)
Джерело: github.com/Vadimkin/ukrainian-air-raid-sirens-dataset (MIT, щоденні оновлення), усі часи UTC.
- `official_data_en.csv`: `oblast, raion, hromada, level, started_at, finished_at, source`; з 15.03.2022; **останній запис 07.09.2026** (відстає).
- `volunteer_data_en.csv`: `region, started_at, finished_at, naive`; тільки обласний рівень; з 25.02.2022; **свіжий до 11.10.2026**. `naive=True` = відбою не було, тривалість штучно +30 хв (1–10% записів).

### Встановлені факти (перевірено на даних)
- Реформа oblast→raion поступова, `REFORM_END = 2025-11-07`.
- Джерела розходяться (згода ~82% погодинно; прифронтові official ≈0.9 vs volunteer 0.3–0.7). **Рішення: volunteer на весь горизонт.**
- Злам у volunteer: к-сть тривог на Київщині ~80 → ~210/міс після реформи → ціль на зайнятості годин (`alert`, `alert_minutes`), не на кількості тривог. **Train з 2025-11-07** (тоді `post_reform` = константа → як фічу не використовуємо).
- Виключено Луганщину та Крим. Відкинуто інтервали ≤0 або >24 год.
- Вироджені області (Дніпропетровщина 81% годин) — поза скоупом.
- Масовані атаки (≥16 областей одночасно): ~790 епізодів, ~120 після реформи.

## Постановка (ЗАФІКСОВАНО)
Скоуп: Kyiv City + Kyivska, Cherkaska, Kirovohradska. Спліт: train 2025-11-07 → T−8тиж, val T−8 → T−4тиж (early stopping, калібрування), **test — останні 4 тижні**, рахується один раз.

### Задача A — ймовірність тривоги (MVP)
Горизонти h ∈ {1, 3, 6, 12, 24}, **direct-стратегія** (окрема модель на кожен h, без рекурсії).
- h ∈ {1, 3}: ціль `any_alert(t, t+h]`.
- h ∈ {6, 12, 24}: вікно «будь-яка тривога за 24 год» насичується (база ≈ 0.9+) → основна ціль **`alert` у годину t+h** (point target); додатково `occupancy(t, t+h]` = частка хвилин під тривогою.
- Головний графік звіту: **skill curve — BSS(h) vs кліматологія та vs Markov** для всіх h. Очікування: автокореляційні фічі вигорають до ~6 год, далі модель → кліматологія; виграш на великих h можливий лише від довгих сигналів (інтенсивність 7–14 днів, `hours_since_mass`, згодом Telegram: стратегічна авіація).

Метрики: Brier, log-loss, BSS, reliability diagram. Кожну — в двох зрізах: **all** та **onset** (`alert(t-1)=0`).
Baselines: кліматологія (частота за годину доби, останні 28 днів, тільки < t), **Markov** P(target | alert(t-1), oblast, hour_kyiv) зі згладжуванням Лапласа (замість persistence — вона дає 0/1 → log-loss = ∞).
Невизначеність: 95% CI для ΔBrier через **block bootstrap по днях**.

Модель: **одна pooled LightGBM** на 4 області (`oblast` — categorical), `objective=binary`; контроль — LogisticRegression. Калібрування Platt на val лише якщо reliability погана (isotonic на ~2.7k точках перенавчиться).
Основний результат = **абляція** на одному алгоритмі: L1 → L1 + L1.5 → (+TG).

### Шари фіч
- **L1 (часовий ряд):** лаги alert 1–24 год, rolling 6 год/24 год/7 днів, година/день тижня (Kyiv; для t і для t+h), тривалість поточної тривоги.
- **L1.5 (сусіди/загрози, з даних тривог):** `alert(t-1)` у сусідів «вгору за маршрутом», `n_oblasts_now(t-1)`, `Δn_oblasts`, `hours_since_mass`, `mass_count_14d`.
  - Kyiv City / Kyivska: Kyivska|Kyiv, Chernihivska, Sumska, Poltavska, Zhytomyrska
  - Cherkaska / Kirovohradska: Poltavska, Dnipropetrovska, Mykolaivska, Odeska (+ одна одній)
- **L2 (Telegram) — НА ПАУЗІ, повертаємось після MVP.** Див. нижче.

### Задача B — тривалість тривоги (stretch, після задачі A)
Постановка як **survival**: на момент t під час активної тривоги (відомий elapsed) прогнозувати залишок — дискретний hazard P(тривога триває ще k хв | elapsed, …) або квантилі залишкової тривалості.
- Фічі: elapsed, година доби, `n_oblasts_now`, mass-флаг, сусіди; з TG — тип загрози (балістика ≈ коротка, шахеди ≈ години).
- `naive=True` записи — тривалість штучна → виключити з цілі або вважати цензурованими. Тривоги, незакриті на кінець даних, — цензуровані.
- **Ризик leakage:** кількість запущених шахедів/ракет ПС ЗСУ публікує ПІСЛЯ атаки → для поточної тривоги недоступна. Легально лише: підсумки *попередніх* атак, або онлайн-повідомлення «N шахедів курсом на …» з `available_at < t`.

## Telegram (`src/telegram_scraper.py` — НЕ протестовано, лише синтаксис)
Запуск тільки локально (Telethon + логін телефоном): `export TG_API_ID=... TG_API_HASH=...`, потім `python -m src.telegram_scraper kpszsu war_monitor --since 2025-01-01` → `data/raw/telegram/<ch>.parquet` (`date_utc, edit_date_utc, available_at, is_forward, views, text`).
Канали: `@kpszsu` (офіційний), моніторингові (`@war_monitor`, `@vanek_nikolaev` — хендли НЕ верифіковані).
Правила leakage для тексту:
1. Фіча в момент t — тільки пости з `available_at < t − buffer` (buffer ≈ 5 хв на затримки).
2. Редагування: `available_at = edit_date` (текст змінився — враховуємо лише після редагування; або беремо першу версію, якщо вона недоступна — відкидаємо пост).
3. Видалені пости не потрапляють у скрап «сьогодні» → survivorship bias; не виправляється, описати в обмеженнях.
4. Ранкові підсумки ПС ЗСУ — це минуле (валідно як «інтенсивність минулої ночі»).
5. Ваги шару вчити на OOF-прогнозах L1 (`TimeSeriesSplit(gap=h)`) лише якщо використовуємо offset-схему; інакше — просто абляція.
